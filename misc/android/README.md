# Android builds

Two GTK 4 + libadwaita builds share one pinned toolchain:

- [`smoke/`](smoke) is a throwaway C app that proves the toolchain before rnote
  is involved (ticket #5). It contains no rnote code.
- [`app/`](app) is the real `rnote-ui` cross-build (ticket #6). It builds the
  desktop Rust workspace unchanged, plus a small meson wrapper that installs the
  app library, translations and GSettings schema into the APK.

Both use [pixiewood][pixiewood] (GTK Android builder), the same builder GTK uses
in its own CI. It generates the meson cross files, the NDK toolchain file, the
Gradle project and the AndroidManifest from a small manifest.

[pixiewood]: https://github.com/sp1ritCS/gtk-android-builder

The app build also needs `cargo` and `rustup` in `PATH`.

`scripts/setup.sh` creates its own meson 1.9.2 virtualenv and installs the SDK,
NDK and pixiewood under `$HOME/Android/Sdk` and
`${XDG_CACHE_HOME:-$HOME/.cache}/rsnote-android`. It does not use `sudo` and
does not modify system packages. Set `ANDROID_HOME` to use an existing SDK
instead.

## Build, install, run

The real rnote UI (ticket #6):

```sh
just android-app-setup        # SDK/NDK/meson/pixiewood + meson configure (downloads several GB)
just android-app-build        # cross-compile rnote-ui + Gradle package
just android-app-install      # adb install -r + launch
just android-app-logcat       # filtered Gtk/Gdk/GLib/rnote/AndroidRuntime log
just android-app-device-check # device, GPU, version, frame stats, memory, crashes, logcat
just android-app-perf-on      # opt into the debug-only perf instrumentation (#12)
just android-app-perf-off     # opt out again
```

The perf instrumentation is off by default, debug-only, and logs frame timings,
touch input-to-snapshot latency and RSS without ever touching note contents. See
[`docs/android/performance.md`](../../docs/android/performance.md) for what it
records and the 20-page device procedure.

The toolchain smoke app (ticket #5):

```sh
just android-setup
just android-build
just android-install
just android-logcat
just android-device-check
```

Artifacts:

- rnote APK: `misc/android/build/rsnote-android.apk`.
- smoke APK: `misc/android/build/rsnote-smoke.apk`.
- Raw Gradle output: `misc/android/{app,smoke}/_pixiewood/android/app/build/outputs/apk/debug/`.
- Device report: `misc/android/build/device-check-<timestamp>.txt`.

`android-app-device-check` records the device model and ABI, Android version,
GPU, the installed app version plus the built APK's SHA-256 and package
identity, a `gfxinfo` summary and recent frame rows, `meminfo`, the crash
buffer, and the filtered logcat. Interact with the app before collecting so the
frame stats have data.

## How the rnote app is built

`app/meson.build` is not a second build system; it is the Android entry point
for the existing workspace:

- `config.rs` is generated from the desktop template with the release app id.
  The generated file is written into `crates/rnote-ui/src/` because Cargo's
  `config` module expects it there, exactly as the desktop meson build does.
- `cargo rustc --bin rnote` builds for the ABI selected by pixiewood's cross
  file. `scripts/cargo-build.sh` wraps it because GTK's Android
  `RuntimeApplication` loads the app with `dlopen()` and resolves an exported
  `main`, so the Rust binary is linked with `-shared -Wl,--export-dynamic` and
  installed as `lib/<abi>/librnote.so`. The wrapper fails the build if `main`
  is not in the dynamic symbol table.
- gtk-rs finds GLib/GTK through pkg-config. The NDK ships no pkg-config, so the
  wrapper symlinks meson's `<name>-uninstalled.pc` files to `<name>.pc`, sets
  `PKG_CONFIG_ALLOW_CROSS=1` and searches only that directory. This is the
  whole gtk-rs Android workaround: no fork and no patch.
- The Rust cargo target depends on GTK's and libadwaita's meson targets, so the
  generated headers and shared libraries exist before pkg-config and the linker
  run.
- Translations are built with `msgfmt` and installed with the `runtime` install
  tag. Meson's `i18n.gettext()` tags `.mo` files as `i18n`, which pixiewood's
  `meson install --tags runtime` would skip. Files land in
  `share/locale/<lang>/LC_MESSAGES/<lang>.mo`; the Android reader scans that
  directory for `*.mo`.
- The GSettings schema is installed to `share/glib-2.0/schemas`; pixiewood
  compiles it and copies it into the asset root. The gresource (UI files,
  icons, CSS) is embedded in `librnote.so` by `build.rs` as on desktop.

Pixiewood copies everything installed from `share/` into APK assets; GTK's
Android runtime copies the assets to the app files dir and points
`XDG_DATA_DIRS` at `files/share`. That covers assets, locales and schemas.

### Dependency gaps handled here

- **librsvg**: the C librsvg crate does not cross-build for Android. The
  Android target depends on pure-Rust `resvg` instead and routes
  `Svg::draw_to_cairo` / `Svg::gen_image` through it. Desktop still uses
  librsvg, so rendering is unchanged there.
- **gettext/libintl**: Android has no libintl and `gettext-sys` would try to
  build GNU gettext from source. The Android target drops `gettext-rs` and uses
  the small `.mo` reader in `crates/rnote-ui/src/i18n.rs`. Desktop still uses
  system gettext.
- **pen sounds**: rodio has no Android backend. The engine's `ui` and `audio`
  features are split; Android enables only `ui`, which compiles a silent
  `AudioPlayer` stub. `Capabilities` also reports pen sounds unsupported, so
  the UI toggle cannot turn them on.
- **renderer**: `env::setup_env()` sets `GSK_RENDERER=gl` on Android before GTK
  starts. There is no cairo fallback: if GL cannot initialize, that is a failed
  gate with logs.

### Emulator

The build only needs the SDK, but the acceptance run needs an emulator with a
working GL stack:

```sh
sdkmanager --sdk_root="$ANDROID_HOME" \
  "emulator" "system-images;android-36;google_apis;x86_64"
avdmanager create avd -n rsnote -k "system-images;android-36;google_apis;x86_64"
emulator -avd rsnote -gpu host
```

Use `-gpu host` on a machine with a GPU. `-gpu swiftshader_indirect` can boot
the app but may fail the GL gate; record that as a device result, not a build
failure.

### Clean checkout and pin changes

```sh
just android-clean        # remove generated build dirs and downloaded subprojects
just android-app-setup
```

`android-app-setup` resets the meson build directories itself; `android-clean`
is only needed after changing a pin, because meson does not advance an existing
`subprojects/` checkout when a wrap revision changes.

## SAF open and save (ticket #8)

Documents are opened and saved through the system picker, never through a
storage path and never with a storage permission.

- `Open`, `Save` and `Save As` use `GtkFileDialog`, which GTK's Android backend
  implements as `ACTION_OPEN_DOCUMENT` / `ACTION_CREATE_DOCUMENT`. The picker
  returns a `GdkAndroidContentFile`, a `GFile` over the content URI.
- The app addresses documents as `gio::File` (ticket #2), so one open/save path
  serves file paths and content URIs. Saves use
  `gio::File::replace_contents_async` with `REPLACE_DESTINATION`.
- Content files report `standard::type` as unknown, and may report a generic MIME
  type. `FileType` therefore treats unknown types as files, classifies by MIME
  type, and falls back to the basename extension;
  `vnd.android.document/directory` is a folder.
- Documents without a local path get no `notify` file watcher
  (`utils::local_watch_path`). The title subtitle shows the content provider
  instead of a folder path.
- The create-document picker ignores `GtkFileDialog`'s suggested name, so a
  freshly created content document is renamed to `<name>.rnote` when it has no
  extension (`utils::ensure_rnote_extension`).
- Open/save filters pass `application/rnote` and, on Android,
  `application/octet-stream`: GTK's Android chooser ignores suffix and pattern
  rules and filters by MIME type, and SAF reports unregistered types as
  octet-stream.
- No storage permission is requested. Pixiewood generates the manifest from
  `com.github.flxzt.rnote.metainfo.xml`; it adds only `REORDER_TASKS`, and file
  access happens through SAF grants.

Device-time gaps:

- GTK 4.22.5 launches create-document with intent type `*/*` (the filter MIME
  types go into `EXTRA_MIME_TYPES`) and drops the suggested filename. A provider
  that rejects `*/*` makes Save As fail; that needs a device check and, if it
  happens, a minimal GTK patch.
- Content URI grants are not persisted yet. Reopening a document after the
  process is killed needs `takePersistableUriPermission` (ticket #10).
- Open → edit → save → reopen through a cloud provider cannot be exercised
  without a device.

## File association / "Open with" (ticket #14)

Android has no MIME mapping for `.rnote`, so a filter for `application/rnote`
alone is not enough: a file manager hands the document over as
`application/octet-stream`. The APK carries two filters on the GTK activity:

- `application/rnote`, generated by pixiewood from the `<mediatype>` in
  `app/com.github.flxzt.rnote.metainfo.xml`;
- `application/octet-stream` with `android:pathPattern=".*\\.rnote"` for the
  `content://` scheme, added by `scripts/patch-manifest.py`. Pixiewood cannot
  express path patterns, so [`build.sh`](scripts/build.sh) runs the patch after
  `pixiewood generate` and before `pixiewood build`.

Both feed the same open path as desktop and as SAF open:

- On a cold start, GTK's `ToplevelActivity` calls `GdkContext.open()` for the
  activity's intent, which emits `GApplication::open`. `RnApp::activate` creates
  the window and `RnApp::open` opens the file in it.
- On a warm start, Android creates a new activity (the activity is
  `launchMode="standard"`), so GTK emits `open` without `activate`. `RnApp::open`
  creates a new window for the document; the new activity binds to that GTK
  toplevel and the previous window stays below in the task history. Document
  identity from ticket #2 still reuses a tab if the same file is opened twice
  in one window.
- `platform::take_launch_file()` still drains a file queued before activation,
  but GTK 4.22.5 delivers intents through `GApplication::open`, so no extra JNI
  glue is needed.

Known limits to check on a device:

- Only `content://` URIs are path-matched. `file://` URIs have no authority, so
  Android cannot match a path, and GTK's content-file conversion rejects
  non-document URIs. Android 7+ file managers use content URIs.
- A provider that reports `application/octet-stream` but does not put the
  `.rnote` name in the URI path (some cloud providers) will not match. Providers
  that report `application/rnote` still do.
- The extension pattern is lowercase.
- GTK's activity does not override `onNewIntent`, so a sender that forces
  `FLAG_ACTIVITY_SINGLE_TOP` while the activity is already on top is not
  handled. Normal `ACTION_VIEW` launches a new activity.

Device check (after `just android-app-install`):

```sh
adb push note.rnote /sdcard/Download/
# Cold: force-stop, then tap the file in Files and choose Rnote.
adb shell am force-stop com.github.flxzt.rnote
# Warm: open one note, leave Rnote in the background, then tap another.
# The second document must open in a new window.
# Inspect the installed filters:
adb shell dumpsys package com.github.flxzt.rnote | rg 'rnote|octet-stream|pathPattern'
```

## Workspace folders (ticket #9)

Workspace folders use the same SAF path as documents, still without a storage
permission.

- `Change Workspace Directory` uses `GtkFileDialog::select_folder`. GTK's Android
  file chooser maps `GTK_FILE_CHOOSER_ACTION_SELECT_FOLDER` to
  `ACTION_OPEN_DOCUMENT_TREE`, so the capability module reports the folder
  picker as supported on Android.
- The picker returns a `GdkAndroidContentFile` over the tree URI. GTK's
  `GtkDirectoryList` enumerates it through `GdkAndroidContentFile`'s
  `DocumentsContract.buildChildDocumentsUriUsingTree` enumerator, so the
  workspace browser lists notes and folders with the same `gio::File` code as on
  desktop. No SAF bridge was needed.
- The workspace entry stores the tree URI (not the content path that
  `GdkAndroidContentFile` reports from `path()`). It is resolved back with
  `gio::File::for_uri` on load.
- Content directories cannot be watched (`GFileMonitor` is unimplemented), so
  the workspace list only monitors native directories. Pull to refresh or
  reselect the workspace after another app changes it.
- The initial workspace is app-specific
  (`<app files>/share/rnote/workspace`, created on first use) instead of the
  desktop home directory. It is the local fallback: notes can be created and
  opened there when a provider cannot enumerate its tree.

Device steps:

1. `just android-app-install`, open the workspace sidebar, and edit the workspace.
2. Press `Change Workspace Directory`, pick a folder through the system tree
   picker, and apply.
3. Check the notes are listed and open one from the list.
4. Rotate or background the app and confirm the workspace survives.
5. Kill the process and reopen it: the grant is not persisted yet (ticket #10),
   so expect to reselect the folder until that lands. The app-specific default
   workspace stays available meanwhile.

Device-time gaps:

- Provider trees differ. Some providers do not implement children queries; the
  list then shows an error/empty state and the app-specific workspace is the
  fallback.
- Tree URI grants are not persisted across process death (ticket #10).
- Moving up from a tree root is disabled, because content files have no parent
  directory.

- shell script syntax, XML well-formedness, pixiewood manifest shape;
- `scripts/patch-manifest.py --self-test` adds exactly one
  `application/octet-stream` + `pathPattern` filter, is idempotent, and keeps
  the manifest parseable; the patch also ran on pixiewood's `manifest.xsl`
  output for the real metainfo;
- meson 1.9.2 configures the app project (with stand-in subprojects), finds the

  the real `po/*.po` files;

  folder display and watcher gating for `content://` URIs (unit tests);

Still requires a machine with the Android SDK, NDK and a device/emulator:

### Lifecycle, autosave and draft recovery (ticket #10)

GTK's Android activity exposes no pause/stop callback. The activity's window
loses focus when it pauses, so `platform::watch_lifecycle()` turns "no app
window is focused" into the pause hook. The pause handler saves every unsaved
tab: documents with an output file are written back, the rest become drafts
under the app cache (`<app cache>/rnote/drafts`). Rotation does not recreate the
activity (pixiewood's manifest sets `configChanges` for orientation and screen
size), so the document and view stay in memory. Desktop never triggers the hook,
so its behaviour is unchanged.

Android sets no `XDG_CACHE_HOME`, and `HOME` is not usable, so `env.rs` derives
the app cache as the sibling of the internal `files` dir that GTK exposes in
`XDG_DATA_DIRS`.

Verified without a device:

- unit tests for the pause/resume edge logic and the Android cache path
  derivation;
- `cargo check -p rnote --all-targets` on desktop and
  `cargo check -p rnote --target aarch64-linux-android --bin rnote`.

Device verification still required:

1. Draw, press Home before the autosave interval elapses,
   `adb shell am kill com.github.flxzt.rnote`, relaunch: the recovery dialog
   offers the draft.
2. Repeat pause/kill/restore ten times: each draft opens with all strokes.
3. Rotate while editing: same document and view, no recovery dialog.
4. Background with a saved document open: the file is rewritten on pause.

Known device-time gaps, deliberately not solved in ticket #6:

- The pinned GTK wrap builds gdk-pixbuf without the librsvg SVG loader, so the
  app's SVG icons may not render. The window and adaptive UI do not depend on
  them.
- Android does not export the Java locale to the POSIX environment, so locale
  selection is best effort (`LANGUAGE`/`LC_*`/`LANG`, then GLib's language
  list). Translations are packaged and the reader works when a locale is
  selected.
- Stylus pressure, IME, and the rest of the spike are later tickets, not part
  of this build wiring. SAF open/save landed in ticket #8 and SAF workspace
  folders in ticket #9 (see above).

## CI

[`.github/workflows/android.yml`](../../.github/workflows/android.yml) builds the
rnote APK on pushes to `main` and on pull requests, in a `fedora:45` container
on `ubuntu-24.04`:

1. installs the host prerequisites listed above;
2. runs `just android-app-setup` and `just android-app-build`;
3. checks that the APK contains `librnote.so` for both ABIs and uploads it as
   the `rsnote-android-apk` artifact (30 days).

Build errors fail the job. No emulator or device tests run in CI, so a green job
does not mean the app runs; use `just android-app-device-check` on hardware.
The first run compiles GTK/libadwaita for two ABIs and can take over an hour.

To reproduce CI locally from a clean checkout, install the host prerequisites
and run the two recipes above; they are the same commands the workflow uses.
`bash -n misc/android/scripts/*.sh` checks the tooling without an SDK.
